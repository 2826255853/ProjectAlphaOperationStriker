# 怪物伤害抗性与易伤方案（待审阅）

状态：第 1–3 步已实施（类别契约、唯一分类结算入口、已有伤害来源接入），第 4–5 步（Prefab 抗性数值、运行时实机核对）未实施。本文件仍是规则来源；实现与本文件不符处记录在 `Assets/Editor/PROJECT_MEMORY.md` 的抗性专节。

## 目标

为怪物提供按伤害类别配置的抗性/易伤，让玩家武器、陷阱直击与持续伤害共用同一结算规则。首版覆盖：火、电、光、远程物理、近程物理、爆炸、冰冻。

## 分类与配置

每笔伤害只指定一个类别，结算一次对应抗性；复合攻击需在攻击来源处选定主类别，首版不拆分伤害分量，也不叠加多个类别的倍率。

建议新增统一的伤害类别枚举，并用怪物侧可序列化配置保存各类别的有符号抗性百分比：

| 类别 | 说明 |
| --- | --- |
| 火 | 火焰直击与燃烧持续伤害 |
| 电 | 电属性伤害；未来由电属性伤害来源调用 |
| 冰冻 | 冰冻类别伤害；不自动施加冻结控制 |
| 光 | 光属性伤害；光攻击可另外施加致盲状态 |
| 远程物理 | 枪械、弓弩等远程实体攻击 |
| 近程物理 | 近战、地刺等近距离实体攻击 |
| 爆炸 | 爆炸冲击与爆炸范围伤害 |

数值采用百分比：`+30%` 表示承受 `70%` 原伤害，`-30%` 表示承受 `130%` 原伤害，`0%` 表示不变。伤害倍率为 `max(0, 1 - resistancePercent / 100)`；最终伤害不得小于零。首版不额外引入抗性上下限，除非审阅时另行指定。

## 分类兼容与数据归属

- 新增七值 `DamageType` 作为玩家、陷阱、状态伤害及抗性配置共用的唯一类别；运行时抗性查表和新伤害入口只认此枚举。
- 保留现有 `TrapDamageType` 及其数值（`Physical=0`、`Fire=1`、`Explosive=2`、`Energy=3`、`Bullet=4`、`Melee=5`），作为旧调用/API 的兼容适配层，不再作为新系统的权威类别。
- 旧值映射固定为：`Fire → Fire`、`Explosive → Explosive`、`Energy → Electric`、`Bullet → RangedPhysical`、`Melee → MeleePhysical`。旧 `Physical` 无法区分远程与近程，保留为无类别兼容伤害，不套用七类抗性；不得把它静默映射成任一物理子类。
- 在 `EnemyHealth` 上保存可序列化的七项抗性百分比配置，作为该怪物实例/Prefab 的权威来源。Prefab 可为不同怪物覆盖配置；运行时实例从所属 Prefab 继承配置；不使用共享 ScriptableObject，避免不同怪物原型意外共用或串改数值。
- 未配置时七项均为 `0%`。抗性是原型配置，不因 `ResetHealth` 改变；运行时克隆应保留来源 Prefab 的配置。

## 现状与实施方向

- 当前 `EnemyHealth` 已有 `TakeDamage(float, TrapDamageType)` 陷阱分类入口；枚举已有火、爆炸等类型，但这不等于已经结算抗性。
- 玩家 hitscan 目前调用 `TakeDamage(float)`，需要在玩家伤害档案/射击结算链补充伤害类别，使玩家与陷阱进入同一个分类伤害入口。兼容旧 `TakeDamage(float)`，旧调用保持原始伤害，不意外套用某个类别。
- 将统一入口放在 `EnemyHealth`：取得目标类别抗性、计算最终伤害、再沿现有扣血/死亡事件流程处理。保留 `Damaged`、`Died` 及现有分类伤害事件的可观察语义，并区分请求伤害与实际扣血量，避免抗性后事件仍报告未调整的原始值。
- `EnemyHealth` 提供统一的分类伤害结算入口：取得 `DamageType` 对应抗性、计算实际伤害，再沿现有扣血/死亡流程处理。保留旧 `TakeDamage(float)` 原始伤害兼容行为，并让旧 `TakeDamage(float, TrapDamageType)` 通过上述固定映射进入新入口；旧 `Physical` 例外地保留无类别行为。
- 玩家武器分类固定为：枪械（含枪械 hitscan）=`RangedPhysical`；近战武器=`MeleePhysical`；手雷、RPG 等爆炸物=`Explosive`。武器档案暴露类别，陷阱调用通过兼容映射或新入口提供类别，不按武器名称猜测属性类别。
- 火、电、光、冰冻类别可以由后续相应伤害来源使用；本方案不因此新增电/冰攻击。光攻击可新增独立致盲状态机制，致盲不是伤害类别，也不由光抗性减免或缩短。
- 保留 `Damaged`、`Died` 的既有可观察语义；分类伤害事件应明确报告最终实际扣除的生命值及新类别，避免把原始请求伤害误报为实际伤害。旧 `TrapDamaged` 的兼容语义需保留或提供等价适配。

## 结算边界

- 火焰直击和 `FireStatusEffect` 的周期伤害都按火抗结算；火抗不改变点燃时长、刷新规则或视觉效果。
- 冰冻抗性只影响冰冻类别的伤害，不代表减速、冻结概率或控制时长抗性；电属性控制效果同理。光抗性只影响光伤害，不影响致盲是否生效或致盲时长。
- 致盲作为独立状态机制允许纳入实现；它不改变伤害归类或抗性公式。致盲具体行为（例如对怪物 AI 的影响）、施加条件和持续时间需在实现该状态时单独定义与测试，不作为抗性参数。
- 爆炸伤害只按爆炸类别结算，不再额外套用远程/近程物理抗性。
- 兼容性调用 `TakeDamage(float)`、非怪物 `SendMessage` 目标及无类别伤害保持现状，不猜测其类别。
- 伤害为零、负数、目标死亡、复用后重置等边界沿用现有生命组件约束；抗性计算不能绕开死亡去重和既有击杀结算。

## 测试与验收

- 单元测试覆盖七类：`0%` 不变、正抗性减伤、负抗性易伤；验证最终扣血及事件报告的实际伤害。
- 验证未配置怪物全类别默认为 `0%`，不同 Prefab 配置互不串值；配置序列化/重载及运行时实例化后保持一致，`ResetHealth` 不改变抗性。
- 验证枪械、近战、手雷/RPG 与现有陷阱映射到指定类别并只应用一次抗性；燃烧持续伤害使用火抗；旧 `Energy`、`Bullet`、`Melee` 映射正确，旧 `Physical` 与无类别调用不套用抗性。
- 验证致盲状态与光伤害结算分离：光抗性改变光伤害，不改变致盲效果或时长；致盲行为按其独立规格测试。
- 回归旧 `TakeDamage(float)` 与 `TrapDamaged` 兼容、死亡事件只触发一次、死亡后不再受伤，以及现有伤害分类/武器伤害测试。
- 验收以 Unity EditMode 测试和项目编译通过为基础；再在代表性怪物上做一次运行时检查，确认抗性数据与实际血量变化一致。

## 分步骤实施方案

以下步骤按依赖顺序执行。每步完成后先通过本步验收，再进入下一步；若实现中发现现有事件或序列化契约与本文不符，应先记录差异并保持旧调用行为，不擅自改变本方案已确认的规则。实施前确认工作区改动并为将修改的 Prefab/资产留好版本控制恢复点；本方案阶段不要求改场景或模型。

### 第 1 步：建立伤害类别与抗性数据契约

- **目标文件**：新增统一 `DamageType` 定义；修改 `Assets/Scripts/TowerDefense/EnemyHealth.cs`，加入可序列化的七类抗性配置及按类别读取配置的接口；检查并修改 `Assets/Scripts/TowerDefense/TrapDamageType.cs` 时保留现有枚举值和兼容映射。
- **最小产物**：`DamageType` 七个类别、旧 `TrapDamageType` 到新类别的固定映射、旧 `Physical` 的无类别例外、默认全零且不依赖共享资产的怪物侧配置。此步不改变实际扣血行为。
- **独立验收**：EditMode 测试验证枚举类别完整、旧枚举数值不变、映射正确、默认值为零，以及不同 `EnemyHealth` 配置实例相互独立；项目编译通过。
- **边界**：不得把旧 `Physical` 猜测映射为远程或近程物理；不加入抗性上下限。

### 第 2 步：在 EnemyHealth 建立唯一分类结算入口

- **目标文件**：`Assets/Scripts/TowerDefense/EnemyHealth.cs` 及其对应测试；必要时更新 `Assets/Editor/TrapDamageClassificationTests.cs`。
- **最小产物**：新增接收 `DamageType` 的统一伤害入口，按 `max(0, 1 - resistancePercent / 100)` 计算实际伤害，再复用既有扣血、死亡去重及击杀结算流程。`TakeDamage(float)` 继续按原始伤害兼容；`TakeDamage(float, TrapDamageType)` 按固定映射转发，旧 `Physical` 继续走无类别原始伤害。
- **事件契约**：保留 `Damaged`、`Died` 及旧分类事件的既有可观察用途；新增或适配的分类事件应同时明确类别与最终实际扣血值，不得把请求伤害伪报为实际伤害。若旧 `TrapDamaged` 的参数/订阅者不能直接表达新语义，增加兼容适配而不静默改变其含义。
- **独立验收**：覆盖七类的零抗、正抗、负抗，零最终伤害、死亡后伤害、事件实际值和死亡只触发一次；确认无类别入口不套用抗性。

### 第 3 步：接入已有伤害来源

- **目标文件**：`Assets/Scripts/FPS/WeaponDamageProfile.cs`、`Assets/Scripts/FPS/FirstPersonController.cs` 中的 `FPSHitscanShooter`，以及现有陷阱伤害调用点和 `Assets/Scripts/TowerDefense/FireStatusEffect.cs`。先搜索全部 `TakeDamage`/`TrapDamageType` 调用点，逐个确认归类后再修改。
- **最小产物**：武器档案暴露权威 `DamageType`；枪械 hitscan 按远程物理、近战按近程物理、手雷/RPG 按爆炸进入统一入口；现有陷阱类别通过兼容映射或新入口只结算一次；燃烧周期伤害按火类别结算。未知或无类别来源保持原行为，不按名称猜测类别。
- **独立验收**：伤害来源测试逐项确认类别与结算入口；验证陷阱及状态伤害不会同时经过旧、新入口而重复扣血；运行既有 `WeaponDamageProfileTests`、`TrapDamageClassificationTests` 和 `FireStatusEffectTests`。
- **边界**：本步不新增电、冰冻攻击，也不改变燃烧刷新、持续时间、视觉或其他附带状态规则；致盲实现不属于此步。

### 第 4 步：验证怪物 Prefab 配置和实例生命周期

- **目标文件**：`EnemyHealth` 序列化实现及相关 Prefab；只有在生成链确实创建/覆盖怪物 Prefab 时，才修改对应 Authoring/生成器，不手工修改其生成结果。
- **最小产物**：七项抗性在 Prefab 上可独立配置；未配置保持零；实例化/克隆继承来源配置；`ResetHealth` 只重置生命状态、不改抗性。先用代表性怪物验证，不批量重写所有 Prefab。
- **独立验收**：序列化重载和运行时实例化后逐项比较配置；两个不同 Prefab 的数值互不影响；执行 `ResetHealth` 前后抗性一致。若需修改 Prefab，先检查并保存改动前恢复点。

### 第 5 步：回归、运行时检查与收尾

- **目标范围**：本方案新增/修改的运行时脚本、编辑期测试和必要 Prefab；不扩展到场景、MapForge 或美术资产。
- **验证顺序**：先运行聚焦 EditMode 测试，再运行项目编译检查；随后在代表性怪物上核对配置值、请求伤害、实际扣血与事件值。最后回归旧 `TakeDamage(float)`、旧 `TrapDamageType` 调用、`TrapDamaged`、死亡去重、死亡后不受伤及既有武器/燃烧测试。
- **完成标准**：类别归类单一且只减免一次；旧调用兼容行为符合本文；Prefab 数据稳定；测试与编译通过；差异审查确认没有意外场景或资产改动。无法运行的测试需列明环境原因及替代验证，不以编译通过代替运行时行为验收。
- **回滚方式**：代码按文件恢复到实施前版本；Prefab/资产恢复到本次改动前保存的版本控制状态。不要通过全量场景导入或重生成无关资产来回滚。

## 已确认决策

- 每笔伤害单一类别；复合攻击由来源指定主类别，不拆分、不重复套用抗性。
- 抗性只影响伤害数值，不改变附带状态的施加或时长；允许新增独立致盲机制。
- 玩家与陷阱统一进入分类抗性结算；旧无类别 API 保持原始伤害兼容行为。
- 抗性不设额外上下限，最终伤害仍不低于零。
- 玩家枪械、近战武器、手雷/RPG 的类别映射按本方案固定规则执行。
- 新 `DamageType` 为唯一权威分类；旧 `TrapDamageType` 保留数值并按本方案映射，旧 `Physical` 不套用分类抗性。
- 抗性配置归属 `EnemyHealth` 并随怪物 Prefab 序列化；七类默认均为 `0%`，不同 Prefab 独立配置。

## 后续单独定义

- 致盲是已允许纳入的独立新机制，但其对怪物 AI 的具体影响、施加条件及持续时间需要在致盲实现规格中另行定义；不影响本方案的伤害类别与抗性规则。
